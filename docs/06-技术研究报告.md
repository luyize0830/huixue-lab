# 《回血实验室》技术研究报告

## 1 问题聚焦

### 1.1 问题描述

典型场景：在图书馆连坐 3 小时，心率比刚坐下时高 12 次/分，过去 1 小时屏幕亮了 40 分钟，此刻 23:40。用户知道该停，却要多做三个决定：做什么、做多久、会不会更累。现有产品都没回答——手环给分数或一句"注意休息"，打卡只记"我休息了"，冥想只提供一种固定动作。

选题依据（竞品缺口）：WHOOP Coach 与 Oura Advisor 依赖厂商自有传感器与云端模型给建议，用户看不到依据也难以修改；Garmin Body Battery 只给能量值；Apple 健康给分数与通用建议；「精力快充」类工具靠手动记录；消费级压力 App 多为单点干预（如呼吸训练）；学术 JITAI 有完整的"状态—干预—反馈"框架，但停留在研究工具。共同的缺口是：建议没有和"我自己的历史"连起来，且多为单信号。

### 1.2 问题抽象

在样本量极小（n=1）、信号有噪声（心率受咖啡、走路、情绪影响）、动作效果异质（同一动作对不同人、不同时段效果不同）的条件下，如何在每个决策点从有限候选集中选一个动作，使"主观评分 + 客观心率变化"的期望最大，同时保持可解释、可退出。这是上下文相关的序贯决策问题，可用多臂老虎机近似。评估是小样本、无对照的个人前后对比，只能给趋势，不能给因果。

### 1.3 问题定位

边界三条：不做疾病筛查与情绪诊断；不做跨天趋势，只做会话与历史对照；不做长周期计划，不给打卡目标。范围收在"5 分钟内可完成"的动作。

### 1.4 问题评估

判断一个方案是否解决问题，看四点：①候选是否可执行（时长、场景、深夜可行性）；②理由是否可追溯到数据；③同类行动的结果是否被记住；④用户能否关掉提醒、清空记录。四条都不需要对照组，可在单机验证。

### 1.5 问题分解

| 子问题 | 处理方式 | 位置 |
| --- | --- | --- |
| 信号可信度 | 缺失即跳过，不用默认值编造 | `SensorSnapshot` |
| 状态判断 | 规则扣分，逐条可解释 | `StateEngine` |
| 动作选择 | 双信号后验 + 探索 | `Recommender` |
| 可行性约束 | 时长、深夜、场景 | `RecommendationConstraints` |
| 反馈 | 自评 1–5 + 心率差 | `ExperimentRecord` |
| 沉淀 | 时段画像、榜单、CSV | `InsightsEngine` |

## 2 相关工作

厂商闭环（WHOOP/Oura/Garmin/Apple）：数据质量与闭环都好，但数据留在厂商侧，建议是"通用实践 + 生理分数"，用户无法追问"为什么是我"。打卡类：门槛低，但没有状态判断，也就没有"此刻"。单点干预（冥想、呼吸、番茄钟）：动作确定可执行，但没有选择。JITAI：把"状态—时机—干预—反馈"形式化，有微随机试验等评估方法，但工程重、依赖研究团队。本项目的差异点：选择权交给用户自己的池子，双信号做小样本个性化，全部在端侧计算。

方法借鉴：`docs/11-qq-bridge逆分析.md` 按公开 README/RULES.md 做四层拆解，只借鉴拆分方式，未引入代码或依赖。

## 3 技术方案

### 3.1 技术方向

方向一：Beta 后验表达"该动作在该状态下对我有效的概率"，采样而非均值，天然带探索。方向二，端侧可解释：所有计算在手机上，理由由数据字段直接拼出，不引入黑箱模型。方向三，诚实降级：取不到就用"—"或演示数据，并在界面标注。

### 3.2 技术选择

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| BLE 标准 HRS | 手环须支持 0x180D；厂商专有数据拿不到 | 采用，小米手环 9 Pro 实测 |
| Gadgetbridge 类开源协议栈 | 需适配多厂商，维护与稳定性成本高 | 不采用 |
| 厂商云 API | 需授权与备案，数据出端，弱网不可用 | 不采用，列为未来 |
| 演示数据 | 零成本，但不可信 | 仅作降级，UI 标"演示数据" |
| 平均分排序 | 简单，但冷启动退化为默认顺序 | 不采用 |
| Thompson 采样 | 需实现 Gamma 采样，结果带随机性 | 采用，冷启动 +0.18 |
| 规则解析对话 | 覆盖有限 | 采用，留 LLM adapter 位 |
| 服务端配对同步 | 需账号、后端与隐私合规 | 不采用；改用 40 bit 离线陪练码 |

为什么用 bandit 而不是平均分：新用户没有记录，平均分会退化成默认顺序，前几个动作被反复推荐，其余永远拿不到数据；Thompson 采样给冷启动动作固定的探索概率，记录变多后自动收敛。为什么不用大模型做对话：本地规则可解释、零延迟、离线可用，大模型会引入网络依赖与幻觉；adapter 位保留，等有评测集再评估。

### 3.3 结果期望

可验证的期望：①任何授权状态下都能给出非空候选，或明确说明为什么没有；②同类记录 ≥3 条后，高分动作排序上升；③每条理由能对应到具体字段；④无网络、无手环时可完整走完五步。

## 4 技术实践

### 4.1 开发框架与依赖

Kotlin + Jetpack Compose，单 Activity 手写导航；Android 官方 BLE、UsageStats、Sensor、Alarm/Notification API；`org.json` 持久化；JUnit4 单测。无 DI、无 Room、无第三方网络或推理库；Beta 采样（Marsaglia–Tsang Gamma、Box–Muller 正态）为自实现，便于注入种子做单测。

### 4.2 技术实践过程

①技术验证（10/29–10/30）：最小 demo 连手环读心率，确认 0x180D/0x2A37 可读、CCCD 可写；踩到 `INSTALL_FAILED_USER_RESTRICTED` 与 test-only 两个坑。②取数抽象：心率、使用统计、步数、时间统一成 `SensorSnapshot`，缺失字段用 null，避免"0 也是有数据"的误判。③逻辑先行：五个引擎全部做成纯函数，先写用例再改实现，接口稳定后 UI 才接。④UI 与降级：12 屏，授权失败走演示滑杆并打角标；提醒 30 分钟唤醒、50 分钟冷却。⑤沉淀：时段画像与 CSV，导出走 FileProvider。

取舍：静息心率用本次会话最低样本近似；久坐只认步数，站着不动算没走动——选择"少报"不"编造姿态"。

## 5 结果验证

①单测：173 个用例全绿，覆盖阈值、约束叠加、CSV、时间戳、位域。②真机：小米手环 9 Pro 心率连续显示，断开提示重连。③设备无关：标准 BLE 0x180D/0x2A37 在 Android 16/HyperOS 实测跳动，不依赖厂商 SDK；无手环降级为使用统计 + 计步 + 时段三信号。④模拟器：AVD 跑通全流程；两台实例用陪练码对齐起点。⑤导出：CSV 在 Excel 打开无乱码。⑥未验证：10 人访谈、两周试用、效果对比、稳定性与耗电。⑦界面结构：v0.6 按 09 的 12 条规则重做导航。⑧设备发现与授权链路：v0.7 把扫描做成独立页，广告含 `0x180D` 或名称命中手环的排前、按 RSSI 排序；Health Connect 补 `PermissionsRationaleActivity` 与三态分流。权限链路的失败比功能缺失更伤体验——"点了没反应"会被记成 App 坏了。⑨角色阈值：v0.10 不照抄档位，另用担心 <70、开心 ≥85；67 分"档位有余量、角色已担心"，4 例钉死 68/70/85。

结论：技术路径可行，产品假设待验证。能证明"端侧可用、逻辑可测、数据诚实"，不能证明"对健康有改善"。

### 5.1 可验证性作为界面的一部分

v0.9 把三条口径印在报告页：每组 <3 次只列不排名；心率变化只统计前后都有值的记录；页末固定「N=1，不可外推，不做因果断言」。

HRV 同样"给不出就空着"：从 `0x2A37` flags bit4 取 R-R，`raw*1000/1024` 换毫秒，过 300–2200 ms 伪迹过滤，算 RMSSD/SDNN；样本不足 8 返回 null，界面四态。心率波动不是医学指标，不做诊断，代价是偶尔显空。

**不静默失败也是界面约束。** v0.9.1 把「失败要说出来」当规则：Key 不以 `sk-` 开头或不足 20 位当场拒存；连不上时气泡必须注明「这是本地规则给的」。证据：真实 Key 下回复带 2 张卡、无尾注；飞行模式同一句降级为本地回复并带尾注。用户能区分「模型在答」与「规则在答」，才有判断力。

⑩从工具到角色：v0.11 换「小夜」，三件事让它不是皮肤：记忆只留 40 轮 + 一句摘要（不发心率与实验记录）；主动性只做当天先开口；边界写死 `Persona`（话短、不喊加油、不装医生）。角色易被打开也易越界，`ChatCodec`/`Persona` 各 7 例钉住。

⑪把"配置"放到用户做决定的那一刻：v0.12 把地址/模型/Key 抽成独立页，接入前可测连通，按 401/402/404/429 给提示；未接入时角色卡也显示。v0.13 称呼做成必填项并进 `Persona`，通知权限挪到登录后。经验：开关藏在第三屏等于没有。

⑫提示词工程：v0.14 把语气从"规矩清单"改成"示例对照"——"别喊加油"难遵守，"他：今天好累 / 你：嗯……累啊"可直接模仿；语气成参数：五档 + 自定义，原样进 prompt，只发自己的模型。

⑬真人感可以工程化：v0.15–v0.17 拆成表达（`Humanizer` 拆 1–3 条、≤30 字、丢客服腔）、节律（`Rhythm` 首条 1200–2600 ms、间歇 600 ms 起）、上下文（`ReplyGate` 8 s 合并、半句 +4 s、14 s 必回；`minutesSinceLast`）、记忆（人设每 4 轮重注）四层，全是纯函数，25 例钉住。框架取自 qq-bridge 公开文档的四层拆解〔已分析源码〕；但"超 120 分钟不回"被否决——沉默即失约，改为"回得慢但一定回"。

⑭主动性要能被单测：v0.18 给主动找人立了六条常量——没聊够 3 小时（状态 <70 时 2 小时）、两次隔 60 分钟、一天最多 3 次、23:00–07:00 静默、有未读不叠加、检查间隔 20 分钟，且没聊过不主动。常量而非"看她心情"，才能被 12 例钉住。"会不会说"是表达，"要不要说"是节律与边界。

⑮语音输出为什么用系统 TTS：v0.19 不打包音色、不要录音权限、不上传音频，代价是音色不可控——取决于用户手机里的语音包。默认关（第一次见面突然出声比安静吓人）；超过 120 字截断加「…」；离开对话页立刻 `shutdown`；念不出必须写明原因（没引擎/没中文包）。TTS 属平台 IO，不做单测，验证靠 logcat 与截图："能调用、语言对"能证明，"好听"不能。
