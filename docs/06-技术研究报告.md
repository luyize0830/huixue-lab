# 《回血实验室》技术研究报告

> 当前交付：v0.23 / versionCode 24，2026-11-03；代码以本地版本分支 `v0.23` 为锚点；GitHub 写入授权未完成，尚未同步。APK 17,720,428 字节；安卓 JVM 234 例、网页 10 例通过。本次未连接真机，历史真机结果不代表新版实测；详见 `v0.23-validation.md`。


## 1 问题聚焦

### 1.1 问题描述

典型场景：图书馆连坐 3 小时，心率比刚坐下高 12 次/分，近 1 小时屏幕亮了 40 分钟，此刻 23:40。用户知道该停，却要多做三个决定：做什么、做多久、会不会更累。现有产品都没回答——手环给分数或一句"注意休息"，打卡只记"我休息了"。

选题依据（竞品缺口）：WHOOP Coach、Oura Advisor 依赖厂商传感器与云端模型，用户看不到依据也改不了；Garmin Body Battery 只给能量值；Apple 健康给分数与通用建议；「精力快充」靠手动记录；消费级压力 App 多为单点干预；学术 JITAI 框架完整但停留在研究工具。共同缺口：建议没和"我自己的历史"连起来，且多为单信号。

### 1.2 问题抽象

样本极小（n=1）、信号有噪声（咖啡、走路都影响心率）、动作效果异质（同一动作对人与时段不同），如何在每个决策点从有限候选里选一个，使"主观评分 + 心率变化"期望最大且可解释、可退出。这是上下文相关的序贯决策，可用多臂老虎机近似；评估是无对照的前后对比，只给趋势。果。

### 1.3 问题定位

边界三条：不做疾病筛查与情绪诊断；不做跨天趋势，只做会话与历史对照；不做长周期计划，不给打卡目标。范围收在"5 分钟内可完成"的动作。

### 1.4 问题评估

判断一个方案是否解决问题，看四点：①候选是否可执行（时长、场景、深夜可行性）；②理由是否可追溯到数据；③同类行动的结果是否被记住；④用户能否关掉提醒、清空记录。四条都不需要对照组，可在单机验证。

### 1.5 问题分解

| 子问题 | 处理方式 | 位置 |
| --- | --- | --- |
| 信号可信度 | 缺失即跳过，不用默认值编造 | `SensorSnapshot` |
| 状态判断 | 规则扣分，逐条可解释 | `StateEngine` |
| 动作选择 | 双信号后验 + 探索 | `Recommender` |
| 可行性约束 | 时长、深夜、场景 | `RecommendationConstraints` |
| 反馈 | 自评 1–5 + 心率差 | `ExperimentRecord` |
| 沉淀 | 时段画像、榜单、CSV | `InsightsEngine` |

## 2 相关工作

厂商闭环（WHOOP/Oura/Garmin/Apple）：闭环好，但数据留在厂商侧，建议是"通用实践 + 生理分数"，用户无法追问"为什么是我"。打卡门槛低，无状态判断。单点干预无选择。JITAI 把"状态—时机—干预—反馈"形式化，有评估方法，但工程重。本项目差异点：选择权交给用户自己的池子，双信号做小样本个性化，全部在端侧算。

方法借鉴：`docs/11-qq-bridge逆分析.md` 按公开 README/RULES.md 做四层拆解，只借鉴拆分方式，未引入代码或依赖。

## 3 技术方案

### 3.1 技术方向

方向一：Beta 后验表达"该动作在该状态下对我有效的概率"，采样而非均值，自带探索。方向二，端侧可解释：计算全在手机上，理由由数据字段拼出，无黑箱模型。方向三，诚实降级：取不到就用"—"或演示数据并标注。

### 3.2 技术选择

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| BLE 标准 HRS | 手环须支持 0x180D；厂商专有数据拿不到 | 采用，小米手环 9 Pro 实测 |
| Gadgetbridge 类开源协议栈 | 需适配多厂商，维护与稳定性成本高 | 不采用 |
| 厂商云 API | 需授权与备案，数据出端，弱网不可用 | 不采用，列为未来 |
| 演示数据 | 零成本，但不可信 | 仅作降级，UI 标"演示数据" |
| 平均分排序 | 简单，但冷启动退化为默认顺序 | 不采用 |
| Thompson 采样 | 需实现 Gamma 采样，结果带随机性 | 采用，冷启动 +0.18 |
| 规则解析对话 | 覆盖有限 | 采用，留 LLM adapter 位 |
| 服务端配对同步 | 需账号、后端与隐私合规 | 不采用；改用 40 bit 离线陪练码 |

为什么用 bandit 不用平均分：新用户没有记录，平均分会退化成默认顺序；Thompson 给冷启动固定探索概率，记录多了自动收敛。为什么不用大模型做对话：本地规则可解释、零延迟、可离线；adapter 位保留。

### 3.3 结果期望

可验证的期望：①任何授权状态下都能给出非空候选或说明为什么没有；②同类记录 ≥3 条后高分动作排序上升；③每条理由能对应到字段；④无网、无手环也能走完五步。

## 4 技术实践

### 4.1 开发框架与依赖

Kotlin + Jetpack Compose，单 Activity 手写导航；Android 官方 BLE、UsageStats、Sensor、Alarm/Notification API；`org.json` 持久化；JUnit4 单测。无 DI、无 Room、无第三方网络或推理库；Beta 采样（Marsaglia–Tsang Gamma、Box–Muller 正态）为自实现，便于注入种子做单测。

### 4.2 技术实践过程

①技术验证（10/29–10/30）：最小 demo 连手环读心率，确认 0x180D/0x2A37 可读、CCCD 可写；踩到 `INSTALL_FAILED_USER_RESTRICTED` 与 test-only 两个坑。②取数抽象：心率、使用统计、步数、时间统一成 `SensorSnapshot`，缺失字段用 null，避免"0 也是有数据"的误判。③逻辑先行：五引擎做成纯函数，先写用例再改实现。④UI 与降级：12 屏，授权失败走演示滑杆并打角标；提醒 30 分钟唤醒、50 分钟冷却。⑤沉淀：时段画像与 CSV，导出走 FileProvider。

取舍：静息心率用本次会话最低样本近似；久坐只认步数，站着不动算没走动——选择"少报"不"编造姿态"。

## 5 结果验证

①单测：212 个用例全绿，覆盖阈值、约束叠加、CSV、时间戳、位域、错误码映射。②真机：小米手环 9 Pro 心率连续显示，断开提示重连。③设备无关：标准 BLE 0x180D/0x2A37 在 Android 16/HyperOS 实测跳动，不依赖厂商 SDK；无手环降级为使用统计 + 计步 + 时段三信号。④模拟器：AVD 跑通全流程；两台实例用陪练码对齐起点。⑤导出：CSV 无乱码。⑥未验证：访谈、试用、效果对比、稳定性与耗电。⑦界面结构：v0.6 按 09 的 12 条规则重做导航。⑧设备发现与授权链路：v0.7 扫描独立成页，广告含 `0x180D` 或名称命中手环的排前；Health Connect 补 `PermissionsRationaleActivity` 与三态分流。权限链路的失败比功能缺失更伤体验——"点了没反应"会被记成 App 坏了。⑨角色阈值：v0.10 不照抄档位，另用担心 <70、开心 ≥85；67 分"档位有余量、角色已担心"，4 例钉死 68/70/85。

结论：技术路径可行，产品假设待验证。能证明"端侧可用、逻辑可测、数据诚实"，不能证明"对健康有改善"。

### 5.1 可验证性作为界面的一部分

v0.9 把三条口径印在报告页：每组 <3 次只列不排名；心率变化只统计前后都有值的记录；页末「N=1，不可外推，不做因果断言」。

HRV 同样"给不出就空着"：从 `0x2A37` flags bit4 取 R-R，`raw*1000/1024` 换毫秒，过 300–2200 ms 伪迹过滤算 RMSSD/SDNN；样本不足 8 返回 null，界面四态。心率波动不是医学指标，不做诊断。

**不静默失败也是界面约束。** v0.9.1 把「失败要说出来」当规则：Key 不以 `sk-` 开头或不足 20 位当场拒存；连不上时气泡必须注明「这是本地规则给的」。证据：真实 Key 下回复带 2 张卡、无尾注；飞行模式同一句降级为本地回复并带尾注。用户能区分「模型在答」与「规则在答」，才有判断力。

⑩从工具到角色：v0.11 换「小夜」，三件事让它不是皮肤：记忆只留 40 轮 + 一句摘要（不发心率与实验记录）；主动性只做当天先开口；边界写死 `Persona`（话短、不喊加油、不装医生）。

⑪把"配置"放到用户做决定的那一刻：v0.12 把地址/模型/Key 抽成独立页，接入前可测连通，按 401/402/404/429 给提示；未接入时角色卡也显示。v0.13 称呼必填并进 `Persona`，通知权限挪到登录后。

⑫提示词工程：v0.14 把语气从"规矩清单"改成"示例对照"——"别喊加油"难遵守，"他：今天好累 / 你：嗯……累啊"可直接模仿；五档 + 自定义原样进 prompt，只发自己的模型。

⑬真人感可以工程化：v0.15–v0.17 拆成表达（`Humanizer` 拆 1–3 条、≤30 字、丢客服腔）、节律（`Rhythm` 首条 1200–2600 ms）、上下文（`ReplyGate` 8 s 合并、14 s 必回）、记忆（人设每 4 轮重注）四层，全为纯函数，25 例钉住；做法参考 qq-bridge 公开文档〔已分析源码〕。"超 120 分钟不回"被否决——沉默即失约，改为"回得慢但一定回"。

⑭主动性要能被单测：v0.18 给主动找人立了六条常量——没聊够 3 小时（状态 <70 时 2 小时）、两次隔 60 分钟、一天最多 3 次、23:00–07:00 静默、有未读不叠加、检查间隔 20 分钟，且没聊过不主动。常量而非"看她心情"，才能被 12 例钉住。"会不会说"是表达，"要不要说"是节律与边界。

⑮语音输出为什么用系统 TTS：v0.19 不打包音色、不要录音权限、不上传音频，代价是音色不可控——取决于用户语音包。默认关；超 120 字截断；离开即 `shutdown`；念不出写明原因。TTS 属平台 IO，不做单测，靠 logcat 与截图证"能调用、语言对"，证不了"好听"。

⑯音频为什么自己合成：v0.20 三段音景用 `AudioTrack` 实时合成（22050 Hz、单声道、PCM16）——雨是多频正弦噪声 + 慢 LFO + 每 1.7 s 雨滴，风是 F3/A3/C4 轻 detune 拍频，呼吸是 C3/G3 + 10 秒包络。四点理由：版权（无音频文件）、包体（不增）、离线、可控（`SynthTest` 4 例）。代价是只做音景做不了歌；第三方无"播放指定歌曲"公开接口，绑定只做"记住 App + 搜索词入剪贴板 + 跳转"，不逆向、不自动播放。

⑰静默降级为什么比报错更伤：用户分不清"没配好""网络不通""地址错""模型乱说"，最后归因成"这 App 是假的"。v0.21/v0.22 把 `ask()` 的 null 拆成 `LlmResult` 三态，用 `LlmErrors` 把 400/401/402/403/404/429/5xx 与域名/超时/SSL 翻成人话；非 JSON 回复当正文渲染并滤掉清单回显。映射全是纯函数，`LlmErrorsTest` 11 例钉住"未配置文案里不许出现连不上"。可修的失败必须可见。

## v0.23 工程修复与验证

外部聊天请求没有跨请求系统记忆；因此每轮必须发送当前性格和必要边界，只可精简示例。一次合批对应一份固定历史，不能把本批既放历史又放当前输入。验证同时覆盖虚拟时钟下的队列时序与本机 HTTP 响应结构，避免只测解析函数却漏掉真实调用链；本次不改变健康阈值或推荐采样算法。
