# 实施任务与里程碑

> R1 / 2026-11-27。本表是下一阶段的执行队列，不是已完成开发清单。工期为有经验开发者的工作日粗估，待首批任务校准，不含等待真实用户的时间。

## 1. 实施顺序

先保证记录可信和升级不丢数据，再做首页与完整流程，随后验证复用需求。沿用 Kotlin / Compose 与现有纯逻辑层；不在这一轮迁移框架、搭云后端或全面更换存储。

## 4. 架构落点

- `logic/`：情境过滤、来源资格、会话状态转换、指标计算和迁移校验，优先纯函数与边界测试。
- `data/`：持久化、外部信号采样、备份、事件原子保存；沿用 Repo 的先保存后发布模式。
- `ui/`：页面展示和动作分发，把新增业务规则从庞大的 App 回调中移出，按本次变更范围逐步拆分。
- `web-demo/`：仍是全 DEMO 的等价展示；生产规则变化时同步，不能替代原生权限、设备和恢复验证。
- `docs/product/prototype/`：只作交互设计附件，与生产实现和旧网页演示明确分开。

## 5. 测试与发布

按仓库 [协作约定](../../AGENTS.md)执行必要检查、提交并同步 GitHub。当前基线为 v0.27 的 267 个 JVM、24 个网页、7 个设备用例；新增实现后按实际结果更新，不能为维持旧数字删测试。

```powershell
.\gradlew.bat testDebugUnitTest assembleDebug assembleDebugAndroidTest --console=plain
node web-demo/selftest.js
python tools/check_delivery.py --require-unit-reports
```

此外须以原生设备执行发布文档规定的测试及正式包冷启动、升级/备份恢复、离线首用。网页通过不能替代原生结果。主模型、真实 Health Connect 或长时通知未测时必须保留未验证标记。

正式产品发生用户可见变更时同步版本号、README、docs/03–08、Release/APK/证据包与桌面交接包；本次规划附件不冒充新的 App 版本。若有用户数据迁移错误、演示污染或正式包无法启动，阻止发布，先修复。

## 6. 范围控制

新增需求必须说明服务哪一个核心步骤、什么证据支持、替换哪个已有任务。未通过试点复用门槛前，不扩大到社交、云同步和重度陪伴。一次评审聚焦一个主要瓶颈；技术测试通过后不无目的重复全量验证。
