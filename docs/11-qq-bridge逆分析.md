# qq-bridge 逆分析：一个"陪聊"系统是怎么被拆成四层的

对象：`https://github.com/Derpyu520/qq-bridge`（3.4k star，MIT/PolyForm 双许可，本地消息桥接工具）。
写这份文档的原因：用户要的是"能每天陪聊的角色"，而 qq-bridge 正是把"大模型 + 人设 + 会话 + 记忆 + 唤醒"工程化的现成样本。我们不是抄它，是把它拆开看哪些决定值得借。

## 一、它的链路

```text
QQ ↔ SnowLuma（OneBot v11）↔ qq-bridge ↔ DeepSeek Harness ↔ 用户自己配置的模型服务
```

关键点：**模型不归它管**。桥接只负责"谁能说话、说什么、说不说、说完怎么审"，模型地址和额度在 DSH 那一层由用户自己配。这条分工决定了它能把"人格"和"能力"分开写。

## 二、四层拆解

| 层 | 负责什么 | 具体机制 |
| --- | --- | --- |
| 协议层 | 收消息、发消息 | OneBot v11；按群聊/私聊各建独立会话；文本、图片、表情、引用 |
| 桥接层 | 谁能说、能不能发 | 白名单（`allow.groups` / `allow.private`）、四模式、管理员命令由桥接硬执行不过模型、发送前正则审计（路径/凭据） |
| 提示词层 | 怎么说话 | 两层拼装：仿真提示词（工具协议、唤醒、分条）+ 人格提示词（`roles/*.md`）；注入上限 8000 字符，首次/变更/会话重建才全量 |
| 模型层 | 生成内容 | DSH + 用户自带模型；失败/离线有队列与降级 |

## 三、七个值得借的决定

1. **行为协议与人格分离**。人格卡里"只写人设，不写工具用法"——因为两代模式的工具协议不同，写进人格卡必然有一代是错的。
   → 我们：`Persona.system()` 只写语气、边界、输出格式；行动清单由 `Persona.user()` 单独给。换成别的模型/接口，人格卡不用改。

2. **注入是节流的，不是每轮都灌**。完整人格卡首次注入，之后每 N 次唤醒只给一句"角色卡已给过"。
   → 我们：上行只带"这句话 + 最近 6 轮 + 一句摘要"，不把 40 轮全塞进去。省钱，也逼近模型的注意力上限。

3. **说不说是 AI 自己决定的**。二代仿真模式不自动转发，AI 自己判断要不要开口、要不要潜水。
   → 我们：`actionIds` 允许为空 —— 她可以只回一句话，不塞卡片。这是"像朋友"和"像客服"的分界线。

4. **管理动作是硬的，不经过模型**。切角色、静默、重置由桥接直接执行，模型改不了自己也绕过不了。
   → 我们：清空记录、撤销授权、关闭提醒都是本地硬操作；模型只能建议，不能替用户决定。

5. **发送前审计**。回复里出现本机路径或凭据特征就整条拦截。
   → 我们：上行永远不带心率、不带实验记录、不带手机号；`Persona` 里写死"不装医生、不诊断、不承诺疗效"。

6. **记忆要能管**。跨会话共享记忆、快照与回滚（衍生版做的）。
   → 我们：本地 40 轮 + 一句摘要，`我的 → 记录` 可一键清空。

7. **配置必须出现在用户做决定的那一刻**。它把模式、人设、白名单、用量全部放在控制台首页，而不是埋在配置文件里。
   → 我们踩过这个坑：v0.9 把"接 API Key"塞进「我的」第三屏，用户直接说"都没有这个选项"。v0.12 改成首页角色卡自己就是入口——她没上线时，卡片上就写着"接入我的模型 →"。

## 四、不照搬的地方

| 它 | 我们 |
| --- | --- |
| 多人群聊里的社会仿真（观望/活跃/试探/退场状态机） | 一个人和一只角色的日常，没有群 |
| 需要 Node、DSH、SnowLuma 三个进程，配置文件 + 控制台 | 一个 APK，装上就能用，配置只有三项 |
| 白名单/令牌/审计是安全刚需（会把消息发到真实群里） | 没有外发通道，安全重点是"不发不该发的数据" |
| 人格卡是 md 文件，管理员编辑 | 人设写进代码，随版本走；用户只能换模型，不能改边界 |

## 五、结论

它教给我们的不是"怎么接模型"（那是最简单的一步），而是**怎么把"她说的话"和"她能做的事"关在两个笼子里**：话由人格决定，事由白名单和审计决定。

我们的产品没有群、没有外发，风险低得多，但同一条原则适用：**角色可以说得很像人，但不能替用户按下任何按钮。**
